# V2 step 3: the judge and calibration implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A blind, swapped, checklist-led vision judge that compares a Bench page built alone with the same page built with Dualkit. It is calibrated against Sam on 20 blind pairs and run across every stored October 2026 pair to get the visible baseline.

**Architecture:** It is a new `judge` area in the private `@dualkit/eval` package with its own CLI (`npm run judge -w @dualkit/eval`). It reads the committed Bench pages in `bench/runs/2026-10/`, re-renders each one full page with Playwright, and asks a vision model through the existing `makeVision` from `packages/cli/src/review/model.ts`. The model scores each checklist point for both pages and then picks. Each pair is asked twice with the sides swapped, and only an answer that holds both ways counts. Calibration writes a self-contained page Sam labels in his browser, then scores the judge against his answers.

**Tech Stack:** TypeScript (ESM), tsx, vitest 3, Playwright 1.55.0 (chromium), pngjs 7.0.0, sharp (already used by bench).

**Spec:** `docs/superpowers/specs/2026-10-22-dualkit-v2-design.md`, Part 4 and "Calls from the builder check". The Bench headline page change waits for Figma sign-off and is not in this plan.

## Global Constraints

- Pass bar, verbatim: "the vision judge agrees with Sam on at least 80% of 20 pairs he judges blind, before any judge number goes on the site." That means at least 16 of 20.
- Blind: neither the model nor Sam sees which side is which. No condition name, model id or file name appears in a prompt, an image or the calibration page.
- Swapped: every pair is judged twice, sides swapped, and "only an answer that holds both ways counts."
- Verdict, verbatim: "the judge scores each checklist point for both pages, then picks. A holistic pick only breaks ties."
- Checklists: 8 to 12 points per Bench screen, written in plain English. Claude writes them, and Sam approves them with the calibration pairs.
- Calibration pairs come from real October Bench pairs: alone against dualkit, same model, same screen, same run.
- No new build calls. The baseline reuses stored October pages.
- Spend: the default judge model is free Gemini (`gemini-flash-lite-latest`). Paid OpenRouter calls go through the shared eval ledger `packages/eval/out/spend-YYYY-MM.json` with a $3 monthly cap. Before the first paid call, confirm that spending credit keeps the 1,000 free requests a day.
- Copy is sentence case and plain English, with no em dashes.
- Commits use `git -c user.email=248309534+selfydev@users.noreply.github.com -c user.name=selfydev commit` and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Stage named files only; never `git add -A`.
- `packages/eval/out/` is gitignored, and all generated pages, screenshots, caches and Sam's answers live there.
- No site change, no publish and no release-surface change in this plan. eval is private.

## Review Focus

1. **A blank or failed page on one side**, such as Laguna's blank screenshots. The non-blank side wins without a model call, recorded as `byDefault: true`. If both sides are blank, the pair is excluded. Blank pages are never used for calibration. Tests are in Task 3 and Task 5.
2. **The free tier runs out mid-run** (HTTP 429, or a daily cap). Failed verdicts are reported as failed, are not counted as ties and are not cached, so a rerun picks up where it stopped. Test in Task 5.
3. **The model returns point ids that don't exist, misses some, or sends malformed JSON.** Unknown ids are ignored, and missing ids count as `na`. Unparseable JSON fails that call, which fails the pair. Test in Task 4.
4. **Position bias**, where the model always picks the first image. The swap turns that into `inconsistent`, never a win. Test in Task 4.
5. **A very tall page.** The screenshot is capped at 2532 px (three 844 px screens), so the image stays within model limits and the two sides stay comparable. Test in Task 3.

### Task 4: the judge core

**Files:**
- Create: `packages/eval/src/judge/judge.ts`
- Test: `packages/eval/src/judge/judge.test.ts`

**Interfaces:**
- Consumes: `Ask` and `Answer` from `../../../cli/src/review/model`, imported by relative path the way `review-run.ts` does, and `Checklist` from Task 1.
- Produces:
  - `JUDGE_PROMPT_VERSION = '1'`
  - `type Mark = 'pass' | 'fail' | 'na'`
  - `type CallVerdict = { points: { id: string; left: Mark; right: Mark }[]; pick: 'left' | 'right' | 'same' }`
  - `buildJudgeAsk(checklist: Checklist, left: Buffer, right: Buffer): Ask`
  - `parseVerdict(text: string, checklist: Checklist): CallVerdict | null`
  - `decide(v: CallVerdict): 'left' | 'right' | 'same'`
  - `type Winner = 'dualkit' | 'alone' | 'tie' | 'inconsistent' | 'failed'`
  - `type PairVerdict = { winner: Winner; byDefault: boolean; calls: (CallVerdict | null)[]; costUsd: number; error?: string }`
  - `judgePair(input: { checklist: Checklist; alone: Buffer; other: Buffer; ask: (a: Ask) => Promise<Answer>; flip: boolean }): Promise<PairVerdict>`

Rules:
- The system prompt says the judge is comparing two screenshots of the same Arabic app screen, labelled image 1 (left) and image 2 (right). It must mark each checklist point pass, fail or na for both images, then pick the better Arabic app, and reply only with JSON in the `CallVerdict` shape. It never mentions Dualkit, models or how the pages were made.
- `decide`: the side with more `pass` marks wins. When they are equal, `pick` decides.
- `parseVerdict` ignores unknown point ids, fills missing ids as `na`, and returns null when there is no JSON, or `pick` or any mark is invalid. It reuses `parseJson` from `../../../cli/src/review/position` if it fits.
- `judgePair`: call 1 puts `alone` on the left when `flip` is false, and call 2 swaps the sides. Each call's `decide` result is mapped back to a condition. If both calls give the same condition, that condition wins. If both say `same`, it is a `tie`. Otherwise it is `inconsistent`. If either call fails, the result is `failed` with the error, and the cost of both calls is summed.

- [ ] **Step 1: Write failing tests**, using a fake `ask` that returns scripted JSON:
  - `points decide before the holistic pick`: left has more passes and the pick is right, so `decide` returns left.
  - `the holistic pick breaks ties`: equal passes, pick right, so right.
  - `a winner must hold both ways`: both calls favour the dualkit image, so `dualkit`.
  - `always picking the first image is inconsistent`: a fake that always gives the left image more passes, so `inconsistent`.
  - `two sames are a tie`.
  - `unknown ids are ignored and missing ids are na`.
  - `malformed JSON fails the pair`: one call returns `not json`, so `failed`, and `costUsd` includes both calls.
  - `the second call swaps the images`: check the image order in the `ask` calls.
  - `the prompt is blind`: `buildJudgeAsk` text and system don't match `/dualkit|alone|model|gemini|minimax/i`.
- [ ] **Step 2:** Run the tests. Expected: FAIL.
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Run the tests. Expected: PASS.
- [ ] **Step 5:** Commit with `feat(eval): blind swapped pairwise judge`.

### Task 5: the judge run, cache and CLI

**Files:**

**Interfaces:**
- Consumes: Tasks 1 to 4, plus `makeVision`, `DEFAULT_REVIEW_MODEL` and `fileLedger` from `../../../cli/src/review/model` and `../../../cli/src/review/spend`, the same ledger path and the `REVIEW_CAP_USD = 3` cap that `review-run.ts` uses (import them, don't copy them).
- Produces:
  - `type JudgedPair = Pair & PairVerdict`
  - `type JudgeSummary = { against: Against; judged: number; dualkit: number; alone: number; tie: number; inconsistent: number; failed: number; excluded: number; byModel: Record<string, Omit<JudgeSummary, 'against' | 'byModel' | 'byScreen'>>; byScreen: …same }`
  - `judgeAll(opts: { pairs: Pair[]; ask; shootFn; seed: number; cache: JudgeCache; log }): Promise<{ results: JudgedPair[]; summary: JudgeSummary; spentUsd: number }>`
  - `headline(s: JudgeSummary): string`, which returns `Dualkit wins N of M blind side-by-sides`, where M counts pairs with a winner, a tie or an inconsistent verdict, but not failed or excluded pairs.
- CLI: `npm run judge -w @dualkit/eval -- run --month 2026-10 --against dualkit|loop [--judge-model provider:model] [--limit N] [--seed N]` writes `packages/eval/out/judge/<month>-<against>.json` and prints the headline plus a by-model and by-screen table.

Rules:
- `flip` per pair comes from a seeded RNG (default seed 1), so a rerun asks the same way.
- Blank handling: one blank side means the other side wins with `byDefault: true` and no call. Two blank sides are `excluded`.
- The cache key is the sha256 of the alone html, the other html, the model id and `JUDGE_PROMPT_VERSION`, stored in `out/judge/cache/<key>.json`. A cache hit costs $0. `failed` verdicts are never cached.
- A failed call that says the budget is spent (`BUDGET_SPENT`) stops the run, and the rest are reported as failed.

  - `failed pairs are not cached and are not ties`: a rerun calls `ask` again for that pair only.
  - `cache hits cost nothing`.
  - `the headline leaves out failed and excluded pairs`.
  - `the same seed asks the same way`.

**Files:**

- Test: `packages/eval/src/judge/calibrate.test.ts`

**Interfaces:**
- Produces:
  - `pickCalibration(pairs: Pair[], isBlankPair: (p: Pair) => Promise<boolean>, n = 20, seed = 7): Promise<Pair[]>`

  - `calibrationPage(items: { slot: number; left: Buffer; right: Buffer; checklist: Checklist }[]): string`
  - `type SamAnswer = { slot: number; pick: 'left' | 'right' | 'same' }`
  - `agreement(key: Key, sam: SamAnswer[], judged: Record<string, Winner>): { agree: number; total: number; passed: boolean; rows: … }`
- CLI:
  - `calibrate make` writes `out/calibration/index.html` and `out/calibration/key.json`, then prints the path.
  - `calibrate score --answers <file>` runs the judge on the 20 pairs (using the Task 5 cache), prints `Judge agrees with Sam on K of 20` plus a row per disagreement, and writes `out/calibration/result.json`.

Rules:
- Selection: alone-against-dualkit pairs only, both sides not blank, two per screen. Models are spread round robin in sorted order so no model has more than 5. The seed is fixed.
- The page is one self-contained file with images as base64 PNGs. It has no pair ids, model names, file names or condition names. Each slot shows the two screenshots side by side, the checklist under them, and three buttons: "Left is better", "Right is better" and "About the same". At the end it has a text box headed "Anything wrong with the checklists?" and a "Save answers" button that downloads `answers.json` with `{answers: SamAnswer[], note: string}`. Answers are also kept in `localStorage` (wrapped in try/catch), so a reload doesn't lose them.
- Agreement: Sam's `same` agrees with the judge's `tie` or `inconsistent`. Sam's left or right agrees only when the judge picked that condition. `failed` never agrees. `passed` is `agree >= 16`.
